# Консультант GigaChat

## Архитектура и хранение

Вкладка «Консультант» встроена в существующий `app/static/index.html` без нового frontend-фреймворка. API находится в `app/api/consultant.py`, системный prompt — в `app/consultant_prompt.py`. Таблицы `consultant_chats` и `consultant_messages` создаются существующим additive-вызовом `Base.metadata.create_all`; каталог, bindings и ML-таблицы не меняются.

Анонимному посетителю выдаётся подписанный HMAC HttpOnly/SameSite cookie. В БД хранится только SHA-256 идентификатора владельца. UUID чата сам по себе не даёт доступа. Для production следует установить уникальный `RC_CONSULTANT_SESSION_SECRET` и включить `RC_CONSULTANT_COOKIE_SECURE=true` при HTTPS. Очистка cookie означает потерю доступа к прежним чатам; переноса между устройствами без аккаунтов нет.

## API

- `GET/POST /api/v1/consultant/chats` — список/создание;
- `GET/PATCH/DELETE /api/v1/consultant/chats/{id}` — история, название, удаление;
- `POST /api/v1/consultant/chats/{id}/messages` — обмен с GigaChat.
- `PATCH /api/v1/consultant/chats/{id}/messages/{message_id}` — редактирование
  пользовательского сообщения и регенерация зависимой ветки.

`request_id` делает завершённую отправку идемпотентной. Сообщения записываются парой только после успешного ответа. История сортируется по автоинкрементному ID. Удаление чата явно удаляет сообщения.

Список чатов возвращает `preview` последнего сообщения и `last_message_id`; сортировка идёт по
последней активности. После успешной отправки интерфейс сразу обновляет локальный preview и затем
сверяет список и активную историю с сервером. Поэтому sidebar не остаётся со старым значением и
после перезагрузки показывает те же данные.

## Названия чатов

Новый чат создаётся как автоматически именуемый (`title_source=auto`). После первого успешного
обмена заголовок определяется детерминированно из первого сообщения без отдельного вызова
GigaChat: распознаются русские формы кухни, гостиной, детской, спальни, ванной/санузла, прихожей,
кабинета, столовой, постирочной/кладовой и балкона/лоджии. Несколько найденных помещений дают
«Несколько комнат», ремонт всей квартиры — «Вся квартира». При отсутствии комнаты используются
консервативные темы вроде «Подбор обоев», «Выбор пола» или «Консультация по материалам».

Ручное переименование устанавливает `title_source=manual`, и такой заголовок больше не
перезаписывается автоматически. Старые строки при additive-миграции помечаются как manual. Если
редактируется первое сообщение автоматически именованного чата, название пересчитывается.

## Контекст и GigaChat

Используется существующий `GigaChatClient`: общий OAuth, модель, CA bundle, асинхронный `httpx`, timeout, retry, rate-limit и budget. Браузер credentials не получает. Настройки по-прежнему задаются через `RC_GIGACHAT_*`. В контекст входят системный prompt и последние 20 сообщений, не более 24 000 символов (настраивается `RC_CONSULTANT_CONTEXT_MESSAGES` и `RC_CONSULTANT_CONTEXT_CHARS`). Полная история остаётся в БД. Structured summary зарезервирован в модели, но пока не генерируется, поэтому очень старые детали за пределами окна следует кратко повторить.

Prompt охватывает детей, питомцев, влажные помещения, кухни, бюджет, аренду, premium, стены, пол, всю квартиру, неоднозначные/конфликтующие требования и потенциально опасные работы. Каталожного lookup у консультанта нет: он не должен придумывать SKU, цены и наличие.

## Интерфейс

Можно вести несколько чатов, переключать, переименовывать и удалять их. Enter отправляет, Shift+Enter добавляет строку. Во время запроса отправка отключена; при ошибке текст остаётся для повтора. Ответы отображаются через ограниченный безопасный Markdown renderer. После содержательной рекомендации появляется «Перейти к калькулятору»: он переключает существующую вкладку без reload, поэтому состояние wizard сохраняется и автоматически не изменяется.

У каждого сообщения есть действие «Копировать»: копируется исходный Markdown через Clipboard API,
с fallback на браузерную команду copy и понятной ошибкой. У пользовательских сообщений также есть
inline-действие «Изменить». Отмена ничего не меняет; пустой текст не отправляется.

При сохранении правки сервер сохраняет сообщения до выбранного пользовательского сообщения,
строит новый контекст и получает новый ответ. До успешного ответа БД не изменяется. Затем сервер
повторно проверяет `expected_last_message_id`: если другая вкладка успела дописать историю,
возвращается 409 и исходная ветка остаётся целой. При успехе старые зависимые сообщения удаляются,
исходное пользовательское сообщение заменяется и новый ответ записывается в одной транзакции.
Повтор того же `request_id` идемпотентен. Сообщения ассистента и чужие чаты редактировать нельзя.

Ошибки отсутствующих credentials, лимита, timeout и временной недоступности переводятся в понятные статусы 503/429/504. Межпроцессная строгая дедупликация одновременного первого запроса не реализована; UI и процессный lock защищают обычный сценарий, а завершённый запрос идемпотентен.

## Параллельность, изоляция и задержки

Состояние браузера хранится отдельно для каждого UUID чата: сообщения, draft, loading, retry ID,
редактирование и ошибка. Отправка и callback захватывают неизменяемый UUID исходного чата.
Переключение вкладки разговора не меняет адресата ответа. Generation-счётчики отбрасывают
устаревшие загрузки истории, а удаление инвалидирует ожидающие UI-операции. Поэтому разные чаты
могут ждать ответ одновременно и показывают собственный индикатор «Консультант печатает…».

На backend ownership проверяется до чтения контекста и повторно после захвата per-chat lock.
История всегда выбирается с фильтром по `chat_id`. Один чат сериализует свои отправки, чтобы второй
запрос увидел первую завершённую пару; разные чаты не блокируют друг друга. Удаление использует тот
же lock и не может оставить частично записанную историю.

`GigaChatClient` общий для процесса и повторно использует OAuth token до истечения срока. Узкий
auth-lock предотвращает два одновременных refresh, но provider completions больше не удерживают
глобальный lock: независимые чаты выполняются параллельно. Безопасные INFO-логи содержат только
chat/request ID, длительности ownership/context/provider/write/total, число сообщений и объём
контекста; prompt, ответы, token и credentials не логируются. Browser console отдельно показывает
network и synchronization time. Ответ рендерится до фоновой сверки sidebar/history.

## Быстрая навигация и cache истории

Причиной замедления списка был N+1: прежний endpoint для каждого чата отдельно загружал всю его
историю только ради preview. Теперь список выполняет один SQL-запрос с последним сообщением каждого
принадлежащего сессии чата; полные истории он не читает. `GET /chats/{id}` выполняет только проверку
владельца и упорядоченную загрузку сообщений выбранного чата. Оба endpoint возвращают безопасный
`Server-Timing` (`db` и `total`), пишут подробность только на DEBUG и WARNING при времени от 250 мс.

Загруженная история кешируется в памяти браузера вместе с `last_message_id`. Повторное открытие с
тем же ID отображает cache синхронно и не делает запрос в течение пяти секунд. После TTL cached
сообщения всё равно показываются сразу, а история обновляется в фоне; изменение sidebar
`last_message_id` инвалидирует cache немедленно. TTL также обеспечивает eventual refresh изменений
из другой вкладки браузера. При быстром переключении единственный history-fetch каждого чата
продолжает выполняться и заполняет именно его cache, даже если пользователь уже ушёл в другой чат.
Это существенно: browser abort не останавливает уже начавшийся синхронный FastAPI/SQLite handler;
прежняя отмена выбрасывала полезный результат, а возврат в чат запускал ещё один серверный запрос.
Последовательность A→B→C→A могла поэтому создать четыре запроса вместо максимум трёх, не прогреть
cache A и при дальнейшем переключении наращивать очередь. Generation token и проверка active chat
не позволяют завершившейся фоновой загрузке перерисовать другой разговор. Повторный click по чату
с уже идущей загрузкой не создаёт второй запрос. `AbortController` теперь используется только когда
snapshot действительно становится недействителен: при отправке/редактировании или удалении чата.
Ошибка или abort всегда снимает history-loading.

Перед ожиданием GigaChat send/edit превращает контекст в обычный неизменяемый список и завершает
read-транзакцию через rollback, возвращая соединение в pool. После ответа ownership и актуальность
истории проверяются снова, затем начинается короткая write-транзакция. Поэтому внешний provider не
держит SQLite connection, а чтение старых историй не зависит от его задержки.

Локальный benchmark (12 чатов, 2 400 сообщений) дал: прежняя эмуляция списка — 13 SQL-запросов и
7,0 мс; новый список — 1 запрос и 3,0 мс; история из 200 сообщений — 2 запроса и 2,5 мс, серверная
часть по `Server-Timing` — 1 мс. Cached переключение создаёт 0 HTTP-запросов. Полноценного browser
timing в CI нет, поскольку Playwright в окружении не установлен; browser console пишет `apiMs`,
`renderMs`, `totalMs`, request count и число сообщений для ручной проверки.

Проверка на реальной локальной базе (~910 МБ, 14 consultant messages) через запущенный HTTP server
дала 43,9 мс для первого списка (40 мс `Server-Timing` DB, включая холодное открытие SQLite) и
3,3 мс для истории (1 мс DB/total). Следовательно, размер истории и GigaChat не объясняют зависание
навигации: подтверждённой причиной повторного ухудшения был клиентский цикл abort/re-request.
HTML shell отдаётся с `Cache-Control: no-cache`, а URL state-script версионирован, чтобы после
обновления браузер не продолжал исполнять старую логику отмены.

Все входы в frontend-массив сообщений (history, edit, send response) валидируют объект, роль и
строковый `content`. Это также очищает `null` из состояния страницы старого формата. Renderer
повторяет безопасную фильтрацию как последний барьер. Optimistic user message добавляется только
через тот же валидатор, удаляется при ошибке и заменяется серверной историей после успешной
синхронизации. Начальный optimistic/edit render находится внутри `try`; `finally` сначала снимает
per-chat loading, а затем независимо восстанавливает DOM и controls. Поэтому даже неожиданная
ошибка отображения не оставляет вечное «Консультант печатает…» и не влияет на другой UUID чата.

Отдельный first-message regression устранён в проверке edit mode. Optimistic user message ещё не
имеет `id`, а при отсутствии редактирования выражение `state.editing?.id === message.id` сравнивало
`undefined === undefined` и ошибочно давало `true`. Следующая строка читала
`state.editing.content` у `null` до HTTP-запроса. Теперь edit mode требует одновременно ненулевой
объект `editing`, сохранённый message ID и совпадение ID. Frontend TypeError/ReferenceError больше
не показываются пользователю буквально: в UI выводится нейтральное сообщение, а name/message/stack
остаются в developer console без текста переписки или credentials.
